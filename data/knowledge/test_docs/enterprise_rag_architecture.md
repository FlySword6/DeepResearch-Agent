# 企业级 RAG 系统架构设计说明

## 背景

企业知识库通常包含制度文档、产品手册、会议纪要、项目复盘、客服记录和技术文档。传统向量检索可以解决语义匹配问题，但在专有名词、编号、日期、指标和短关键词检索上容易漏召回。因此，企业级 RAG 更推荐采用混合检索，即向量召回与关键词召回并行执行，再通过融合排序得到最终候选结果。

## 推荐架构

一个稳定的 RAG 流程通常包含文档解析、父子分块、Embedding、向量索引、BM25 索引、RRF 融合排序、上下文组装和答案生成。父子分块的关键思想是：child chunk 用于精准检索，parent chunk 用于补全上下文。这样既能命中细粒度问题，也能避免答案只看到局部片段。

## 检索流程

用户问题进入系统后，首先并行执行两路召回。向量检索适合处理语义相似问题，例如“如何降低模型幻觉”；BM25 适合处理关键词明确的问题，例如“RRF 参数”“Milvus collection”“2026 Q2”。两路结果分别打分后，使用 Reciprocal Rank Fusion 进行融合。RRF 不直接比较不同检索器的原始分数，而是根据排名位置计算融合得分，因此对不同分数尺度更稳健。

## 质量控制

RAG 系统需要记录 source、doc_type、chunk_id、parent_id、score 和引用来源。生成答案时，应将引用信息保留到报告末尾，便于用户追溯。对于高价值知识库，还应支持按来源删除、重新导入、版本号管理和检索测试。

## 结论

Milvus + BM25 + RRF + 父子分块是一种适合企业知识库的通用方案。它兼顾语义理解、关键词精确匹配和上下文完整性，比单一路向量检索更适合复杂研究任务。
